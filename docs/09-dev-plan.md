## Находки шага 1

Интеграционные тесты на настоящем Synapse выявили два отличия от документации. Они исправлены и отражены в [03-architecture.md](03-architecture.md#32-контекст-случая-state-событие):

1. **Комнаты версии 12** (по умолчанию в Synapse 1.162). Создателя комнаты нельзя указывать в `power_levels.users`. Кроме того, `createRoom` при ошибке успевает создать комнату с псевдонимом — поэтому сервис достраивает такие комнаты, а не создаёт вторую.
2. **State-события с ключом `@…`** может писать только сам пользователь. Поэтому роли участников хранятся одним событием `ru.vendor.case.roles`.

## Находки шага 1б

1. **Приглашение пользователю, который ещё не входил,** Synapse принимает. Значит, РИС/ЛИС может передавать участников по логину, без предварительной регистрации в мессенджере.
2. **Пауза повторов Application Service — до 512 секунд.** Если сервис контекста был недоступен, Synapse досылает события не сразу. Сервис при старте вызывает ping Application Service, и Synapse досылает накопленное немедленно ([03-architecture.md, раздел 10](03-architecture.md#10-эксплуатация)).
3. **Недоступная ЛИС задерживает все события сервису.** Пока заявка не доставлена в ЛИС, сервис просит Synapse повторить транзакцию. Для PoC это приемлемо; в продукте нужна исходящая очередь.

## Находки шага 2

1. **Имена пользователей** берутся из профиля Matrix. По умолчанию Synapse ставит туда логин, поэтому нужна синхронизация профилей из каталога (Keycloak/AD) — задача шага развёртывания. На стенде имена задаёт `pnpm dev:users`.
2. **Размер сборки** — около 1 МБ JavaScript (300 КБ в gzip), в основном matrix-js-sdk. Для встраивания (шаг 4) нужно разделить код: панель чата должна грузиться быстро.
3. **Приглашение не содержит контекста случая** — в нём есть только тип комнаты и название. Список показывает такие чаты как «Чат случая» до входа; карточка появляется после входа.

## Правила разработки

- Каждое изменение сервиса контекста — с модульным тестом. Поведение на сервере проверяется интеграционным тестом (`pnpm test:it`).
- Структурированные сообщения — только через схемы `packages/protocol`, у каждого обязателен текстовый `body`.
- Никаких ПДн в логах и тестовых данных: только вымышленные данные и маски.
- Новые зависимости — с лицензией Apache-2.0, MIT или BSD. AGPL, GPL и MPL не берём в ядро (реестр ПО).

## Находки стенда

1. **Лимит входов Synapse по адресу.** По умолчанию — 5 входов, затем один раз примерно в 5 минут. Тестировщики из одной сети выходят в интернет с одного адреса и упираются в него. На стенде лимит по адресу мягче, а защита от подбора пароля — на неудачных попытках по учётной записи. Для продукта то же решение нужно согласовать с ИБ.
2. **Корпоративный прокси с подменой сертификатов** ломает сборку образов. Стенд принимает корневой сертификат прокси как секрет сборки (`BUILD_CA_FILE`), в образ он не попадает.
3. **Сигнализация LiveKit через тот же домен.** SDK сохраняет путь в адресе (`wss://домен/livekit`), поэтому отдельное DNS-имя для звонков не нужно; медиа идёт напрямую на UDP 7882 / TCP 7881.

## Находки шага 4

1. **Контекст случая в приглашении.** Synapse добавляет выбранные state-события в приглашение (`room_prejoin_state.additional_event_types`). Включили для `ru.vendor.case.context`: счётчики РИС и список чатов видят новый чат случая до входа в него.
2. **Невидимый фрейм не получает `requestAnimationFrame`.** Браузер не вызывает его в скрытых фреймах с другого домена, и фрейм-счётчик «засыпал». Перерисовка клиента теперь по таймеру.
3. **Строгий режим React вызывает `useMemo` дважды.** Второй мост `postMessage` без обработчиков отвечал хосту ошибками. Мост — один на страницу, вне React.
4. **Два фрейма — два подключения к серверу.** Панель и счётчики сейчас синхронизируются отдельно. В продукте их можно объединить общим фреймом (BroadcastChannel или SharedWorker).

## Находки шага 6

1. **Синтезированная речь вместо микрофона.** Chromium подаёт WAV-файл как микрофон (`--use-file-for-fake-audio-capture`), у каждого участника свой браузер и свой голос. Так весь путь — WebRTC, LiveKit, агент, распознавание, LLM, чат — проверяется автоматически. Vosk распознаёт синтезированные фразы почти без ошибок; на живой речи врачей нужен замер WER.
2. **В событиях Matrix запрещены дробные числа** (канонический JSON): Synapse отвечает 400 на время фрагмента «6.5 с». Время в стенограмме — целые миллисекунды. Поддельный Matrix в модульных тестах теперь отвергает дробные числа так же.
3. **Маленькая LLM (1,7 млрд параметров) на 4 vCPU** готовит черновик за 15–30 с, но без опоры на пример оставляла «Решение» пустым и брала «цель» из названия случая. Помогли: определения разделов и один вымышленный пример в инструкции; ответ строго в JSON (`response_format`); в модель уходит только стенограмма, сведения о случае подставляет система.
4. **Ссылки ставит и маленькая модель, но не всегда верно.** Сервис проверяет каждое утверждение сам: ссылки только на существующие фрагменты; позиция участника — только на его реплики; не меньше половины значимых слов утверждения есть в цитируемых фрагментах. Иначе утверждение в черновик не попадает.
5. **Ресурсы профиля «только CPU»:** распознавание (Vosk, kaldi-ru) — около 6 ГБ памяти и справляется в реальном времени с двумя дорожками на 4 vCPU; LLM (llama.cpp) — около 5,5 ГБ. Для стенда с ИИ нужна машина на 16 ГБ.
6. **Индикатор стенограммы нельзя подделать снятием.** Состояние звонка в комнате могут менять участники, поэтому клиент показывает индикатор и по факту: в звонке есть участник-агент (токены агентам выдаёт только сервис контекста). Карточки стенограммы и черновика клиент рисует только от сервиса — создателя комнаты.

## Находки шага 3б

1. **Подтверждение нельзя подделать сообщением.** Событие `ru.vendor.ack` может отправить любой участник, поэтому решает сервис: засчитывает его только от адресата или подключённого эскалацией и пишет итог в state-событие уровня 100. Попытка участника записать статус сам — `403` от Synapse (проверено интеграционным тестом).
2. **Приглашённый эскалацией должен сразу видеть, что его ждёт.** Статус находки добавлен в `room_prejoin_state`, а сервис пишет статус до приглашения — иначе в приглашение попадает старый статус без нового адресата. Заведующий видит «!» в списке ещё до входа в чат.
3. **Доступ через эскалацию.** У заведующего может не быть доступа к случаю в РИС. Раз сервис сам пустил его в чат, ссылка из РИС тоже открывает чат: приглашённому или вошедшему сервис не отказывает (кроме отозванных).
4. **Сроки — на сервере, а не в клиенте.** Таймер в сервисе с арендой шага в PostgreSQL (`FOR UPDATE SKIP LOCKED`): два экземпляра не выполняют шаг дважды (проверено параллельными вызовами), упавший экземпляр — шаг повторяется после аренды; сообщения в чат идемпотентны по ID транзакции.
5. **Сообщение формирует клиент — ему нельзя доверять расширение доступа.** Явные адресаты находки из чата — только участники случая, план эскалации — только из настройки подключения; иначе через «адресата» можно было бы пригласить в чат случая постороннего. Находкам из РИС/ЛИС (доверенный источник) можно указывать и людей, и план.
6. **Звонок на пост** — дело телефонии РИС/ЛИС: сервис передаёт шаг обратным вызовом. Для РИС/ЛИС уровня 1 в чате пишется «телефония не подключена, позвоните вручную» — это видно и в карточке находки.

## Находки нагрузочного теста

Подробно — [11-load-test.md](11-load-test.md).

1. **Один процесс Synapse — потолок около 3,5 новых чатов в секунду** на 4 vCPU (чат — около 12 событий состояния). Это в 15 раз больше пикового часа региона, но меньше цели 5/с: её закрывают воркеры записи событий.
2. **Массовое переподключение — главный риск.** 240 клиентов, одновременно начавших синхронизацию с нуля, ждали около 2 минут. Веб-клиент без локального хранилища начинает с нуля при каждой загрузке страницы. Simplified Sliding Sync отдаёт первые 20 из 200 комнат за 0,1–0,2 с — переход на него (шаг 7) приоритетнее.
3. **Сервис контекста обрабатывал пакет событий строго по одному.** Теперь события разных случаев — параллельно, одного случая — по порядку.
4. **Сервис контекста не узкое место:** ≤ 3 % процессора, транзакции от Synapse — ≤ 1 мс.
5. **Переход веб-клиента на Simplified Sliding Sync** (прогон 3): первый экран при 200 комнатах — 0,15 с вместо 6 с; доставка при 240 клиентах и реальном потоке — p95 265 мс вместо 721 мс (в цели); 240 клиентов, начавших разом, — 43 с вместо 126 с. Остаток шторма — воркеры синхронизации.

## Находки встраивания в ЛИС

1. **Simplified Sliding Sync в Synapse не считает непрочитанное:** `notification_count` всегда 0 (в коде Synapse: «уведомления правильно считает только клиент»). После перехода на Sliding Sync счётчики в папках, в списке чатов и бейджи РИС/ЛИС показывали только приглашения — тест бейджа РИС проходил за счёт приглашения. Теперь непрочитанное считает клиент: чужие сообщения после отметки о прочтении или своего сообщения.
2. **Свёрнутое окно `launcher` читало сообщения:** документ фрейма для браузера «видим», даже когда окно скрыто. SDK сообщает чату, открыто ли окно (`view.visible`); свёрнутый чат не отправляет отметки о прочтении.
3. **Отметка «прочитано» общая для всех сеансов пользователя:** открытая вкладка того же врача сразу читает новое сообщение — и бейджа во встроенном чате не будет. Это верно, но тесты одного случая открывают разных пользователей.

## Находки архива

1. **Выведенный из комнаты остаётся в списке Sliding Sync.** Synapse отдаёт комнаты, из которых пользователя вывели (kick), пока он их не «забудет» (`/forget`), — иначе архив не разгрузил бы синхронизацию. Сервис не может «забыть» за пользователя, поэтому это делает клиент; мобильным клиентам — то же правило.
2. **Гонка при возврате из архива.** Случай снова открыт: сервис снимал архив, а отметку «закрыт» сбрасывал только в конце синхронизации со снимком; проход архива посередине отправлял чат обратно в архив и снова выводил участников. Теперь снятие архива сразу сбрасывает и «закрыт» (модульный тест воспроизводит гонку). Сквозной тест ловил её примерно в половине прогонов на Synapse с воркерами.
3. **Приглашение в «забытую» комнату matrix-js-sdk отбрасывает:** сервер присылает его как продолжение, а для неизвестной клиенту комнаты SDK принимает только первые данные. Клиент помечает такое приглашение первыми данными; после входа сервер сам присылает комнату целиком.
4. **Поиск по архиву без учёта регистра:** база сервиса контекста создана с `lc_ctype C`, и `ILIKE` не сравнивает кириллицу без учёта регистра. Номер и название хранятся ещё и в нижнем регистре.
5. **Одновременный возврат многих пользователей** (приглашение и вход — два события на возврат): 50 возвратов разом — p95 5,7 с на одном процессе Synapse и 4,7 с с воркерами; больше всего времени уходит в сервисе контекста (проверка прав и приглашение). По одному — 0,4–0,6 с, в цели.

## Находки Synapse с воркерами

1. **Задержка репликации видна клиентам.** Изменение, сделанное через главный процесс, воркер синхронизации видит через доли секунды: «забытая» комната ещё раз приходит в список, а запрос ленты сразу после входа в комнату может вернуться пустым. Клиент это переживает (следующий ответ синхронизации), а тесты ждут результата, а не проверяют мгновенно.
2. **Порядок маршрутов Caddy.** Блоки `handle` с путём (`/_matrix/*`) Caddy ставит раньше блоков с именованным сопоставителем (`path_regexp`), поэтому выбор «синхронизация → воркеры» сделан внутри блока `/_matrix/*`. Порядок проверен через `caddy adapt`.
3. **Redis сменил лицензию** (7.4+ — RSAL/SSPL, 8 — ещё и AGPLv3). Взят Valkey (BSD-3) — тот же протокол; подходит и LiveKit.
4. **Слушатели воркеров — только IPv4** (`bind_addresses: ["0.0.0.0"]`): по умолчанию Synapse слушает `::` и `0.0.0.0` одновременно, и в контейнере второй адрес уже занят первым.
5. **Песочница ЛИС повторяла номера заявок после перезапуска**, а сервис контекста помнит обработанные события 7 дней — статусы «новой» заявки отбрасывались как повтор. Номера теперь не повторяются между перезапусками.

## Находки Tuwunel

1. **Sliding Sync отдаёт первичные данные комнаты только новому соединению.** Принятое приглашение и вывод из комнаты в текущем соединении приходят без истории и состояния, подстановка `['*', '*']` в `required_state` молча игнорируется. Отсюда 4 из 13 сквозных тестов на Tuwunel. **Обход сделан** — подробно в [11-load-test.md, 7.4](11-load-test.md#74-совместимость): данные незнакомой комнаты — как начальные, по признакам неполного чата — новое соединение, явный список состояния открытого чата, догрузка короткой ленты, архив — по причине вывода.
7. **В приглашении нет своих типов состояния** (аналога `room_prejoin_state` нет), поэтому бейдж нового исследования в РИС не появлялся до входа. Обход: сервис кладёт снимок контекста случая, находок и архива в само приглашение (`ru.vendor.prejoin_state`), клиент дополняет им `invite_state`.
8. **Два цикла синхронизации одного входа на одном соединении получают 400** (Tuwunel строго проверяет `pos`): панель чата и счётчик бейджей во встраивании, две вкладки. Обход: своё соединение (`conn_id`) у каждой вкладки и фрейма — наименьший свободный номер через Web Locks. Попутно исправлено: клиент, остановленный до запуска синхронизации (React в режиме разработки монтирует компонент дважды), всё равно запускал второй цикл.
9. **После обхода сквозные тесты зелёные на обоих серверах:** Tuwunel — 14 прошли, 2 пропущены; Synapse — 15 прошли, 1 пропущен.
2. **Запись без fsync.** RocksDB подтверждает сообщение до записи на диск: падение процесса данные не теряет, отключение питания — может.
3. **Admin API Synapse нет.** Пользователей стенда и тестов регистрирует `registerUser` по токену регистрации; первый зарегистрированный пользователь становится администратором сервера.
4. **Вход через Keycloak требует discovery** даже при явно заданных адресах — иначе 500. Адрес discovery внутренний; Keycloak (`KC_HOSTNAME_BACKCHANNEL_DYNAMIC`) отдаёт браузеру адрес входа localhost:8180.
5. **`docker stats` показывает процессор Tuwunel нулём** — загрузку берём из cgroup.
6. **Образ** — `jevolk/tuwunel` с Docker Hub: скачивание из GitHub Container Registry закрыто политикой сети стенда разработки.

## Находки консилиума

1. **Сессии «Секретаря» живут в памяти сервиса контекста.** После перезапуска сервиса посреди стенограммы индикатор «Стенограмма (ИИ)» оставался в комнате навсегда, а «Остановить» отвечало 409. Теперь остановка без сессии снимает индикатор и честно пишет, что запись не сохранена. В продукте сессии — в PostgreSQL.
2. **Развёрнутый звонок закрывает ленту.** Председатель не мог переключить случай, не свернув видео; текущий случай и «Следующий случай» теперь и в панели звонка.
3. **Комнату консилиума сервис создаёт по событию, а обработанные события помнит 7 дней.** Песочница досылает консилиум с меткой запуска в ID события; `POST /demo/consilium` назначает ещё один консилиум (повторный показ, сквозной тест).
4. **`aria-disabled` у кнопки делает её недоступной** и для экранного диктора, и для Playwright. «Принять в протокол МИС» до проверки всех разделов нажимается и показывает подсказку — как в макете.
5. **Стенограмма консилиума не уходит в чаты случаев**: в ней обсуждение других пациентов, а состав чата случая шире или уже состава консилиума. В чат случая — только принятый протокол без ссылок на стенограмму.

## Находки единого входа

1. **Строгий режим React вызывает инициализаторы состояния и эффекты дважды.** Одноразовый `loginToken`, прочитанный и убранный из адреса внутри инициализатора, терялся. Токен читается один раз при загрузке модуля, а обмен на сессию дедуплицируется по токену.
2. **Synapse требует `https` у адресов OIDC.** В окружении разработчика — `skip_verification` (только там). На стенде браузер идёт в Keycloak по https, а Synapse — напрямую внутри сети стенда; издатель токенов проверяется, адрес Keycloak для токенов задаётся через `KC_HOSTNAME`, внутренние запросы разрешены `KC_HOSTNAME_BACKCHANNEL_DYNAMIC`.
3. **Страницу входа организации нельзя показать во фрейме РИС/ЛИС** (Keycloak запрещает встраивание). Во фрейме вход открывается во всплывающем окне; окно возвращает одноразовый токен фрейму сообщением с проверкой origin. Общее хранилище не используется: у фрейма на чужом домене оно отделено (разделение хранилища третьих сторон в браузерах).
4. **Образ Keycloak** взят с Docker Hub (`keycloak/keycloak` — зеркало quay.io), с фиксацией по digest.
