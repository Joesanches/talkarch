## Находки шага 1

Интеграционные тесты на настоящем Synapse выявили два отличия от документации. Они исправлены и отражены в [03-architecture.md](03-architecture.md#32-контекст-случая-state-событие):

1. **Комнаты версии 12** (по умолчанию в Synapse 1.162). Создателя комнаты нельзя указывать в `power_levels.users`. Кроме того, `createRoom` при ошибке успевает создать комнату с псевдонимом — поэтому сервис достраивает такие комнаты, а не создаёт вторую.
2. **State-события с ключом `@…`** может писать только сам пользователь. Поэтому роли участников хранятся одним событием `ru.vendor.case.roles`.

## Находки шага 1б

1. **Приглашение пользователю, который ещё не входил,** Synapse принимает. Значит, РИС/ЛИС может передавать участников по логину, без предварительной регистрации в мессенджере.
2. **Пауза повторов Application Service — до 512 секунд.** Если сервис контекста был недоступен, Synapse досылает события не сразу. Сервис при старте вызывает ping Application Service, и Synapse досылает накопленное немедленно ([03-architecture.md, раздел 10](03-architecture.md#10-эксплуатация)).
3. **Недоступная ЛИС задерживает все события сервису.** Пока заявка не доставлена в ЛИС, сервис просит Synapse повторить транзакцию. Для PoC это приемлемо; в продукте нужна исходящая очередь.

## Находки шага 2

1. **Имена пользователей** берутся из профиля Matrix. По умолчанию Synapse ставит туда логин, поэтому нужна синхронизация профилей из каталога (Keycloak/AD) — задача шага развёртывания. На стенде имена задаёт `pnpm dev:users`.
2. **Размер сборки** — около 1 МБ JavaScript (300 КБ в gzip), в основном matrix-js-sdk. Для встраивания (шаг 4) нужно разделить код: панель чата должна грузиться быстро.
3. **Приглашение не содержит контекста случая** — в нём есть только тип комнаты и название. Список показывает такие чаты как «Чат случая» до входа; карточка появляется после входа.

## Правила разработки

- Каждое изменение сервиса контекста — с модульным тестом. Поведение на сервере проверяется интеграционным тестом (`pnpm test:it`).
- Структурированные сообщения — только через схемы `packages/protocol`, у каждого обязателен текстовый `body`.
- Никаких ПДн в логах и тестовых данных: только вымышленные данные и маски.
- Новые зависимости — с лицензией Apache-2.0, MIT или BSD. AGPL, GPL и MPL не берём в ядро (реестр ПО).

## Находки стенда

1. **Лимит входов Synapse по адресу.** По умолчанию — 5 входов, затем один раз примерно в 5 минут. Тестировщики из одной сети выходят в интернет с одного адреса и упираются в него. На стенде лимит по адресу мягче, а защита от подбора пароля — на неудачных попытках по учётной записи. Для продукта то же решение нужно согласовать с ИБ.
2. **Корпоративный прокси с подменой сертификатов** ломает сборку образов. Стенд принимает корневой сертификат прокси как секрет сборки (`BUILD_CA_FILE`), в образ он не попадает.
3. **Сигнализация LiveKit через тот же домен.** SDK сохраняет путь в адресе (`wss://домен/livekit`), поэтому отдельное DNS-имя для звонков не нужно; медиа идёт напрямую на UDP 7882 / TCP 7881.
