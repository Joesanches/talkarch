# Нагрузочный тест PoC: результаты

> Прогон 08.10.2026. Инструмент и порядок запуска — [tools/load](../tools/load/README.md). Цели — [03-architecture.md, 9.4](03-architecture.md#94-проверка-в-poc). Сырые результаты — `tools/load/results/load-r1.json` (основной прогон) и `load-r2.json` (реалистичная частота, после доработки).

## 1. Коротко

Стенд — **одна машина на 4 vCPU и 15 ГБ**: Synapse 1.162 **одним процессом, без воркеров**, PostgreSQL 16, сервис контекста и генератор нагрузки. Это в разы слабее продуктивной конфигурации из [03-architecture.md, 9.2](03-architecture.md#92-сервер), поэтому результаты — нижняя граница и поиск узких мест, а не сайзинг.

| Цель (p95) | Результат на стенде | Вывод |
|---|---|---|
| Создание чата случая ≤ 1 с | 0,85 с при 0,5 чата/с ✓; 1,1 с при 1/с; 3,0 с при 2,5/с; при 5/с — очередь (потолок ~3,6/с) | Реальный пик (до 0,2 чата/с в регионе) — в цели с запасом. Целевой пик 5/с — нет: один процесс Synapse записывает ~45 событий/с. Нужны воркеры записи событий |
| Доставка сообщения ≤ 300 мс | 60 клиентов, 2 сообщения/с — **108 мс** ✓; 240 клиентов, 2–10/с — 0,7–1,3 с; 30/с — перегрузка | Медиана всегда в цели (90–125 мс), хвост растёт с числом клиентов: один процесс Synapse и пишет, и обслуживает сотни синхронизаций. Нужны воркеры синхронизации |
| Холодный старт клиента ≤ 1,5 с | 20 комнат — 1,0 с ✓; 200–250 комнат обычной синхронизацией — 6,1–6,6 с ✗, **через Sliding Sync — 0,16 с** ✓ | Для врачей с сотнями комнат — только Simplified Sliding Sync |
| Возврат в архивную комнату ≤ 1 с | Не проверялось | Архивирование ещё не реализовано |

**Главная находка — массовое переподключение.** 240 клиентов, одновременно начавших синхронизацию с нуля, ждали ответа около **2 минут** (p50 126 с). Так выглядит начало смены или перезапуск сервера. Сейчас веб-клиент начинает с нуля при каждой загрузке страницы (без локального хранилища). Решение: Simplified Sliding Sync и локальное хранилище в клиенте (шаг 7), воркеры синхронизации на сервере.

**Сервис контекста не узкое место:** ≤ 3 % процессора, 19 тыс. транзакций от Synapse обработаны за ≤ 1 мс (p95), ошибок нет. Узкое место — однопроцессный Synapse: при создании чатов и при 30 сообщениях/с он упирается в одно ядро (116 % у контейнера).

## 2. Стенд и метод

- **Данные основного прогона:** 245 пользователей; 1900 чатов случаев по 3 участника (+ сервис); у каждого из 240 «врачей» 20 чатов, у 5 «заведующих» — по 200; 37 тыс. событий, база Synapse — 235 МБ.
- **Прогон 2** — поверх данных первого: ещё 120 случаев и 100 чатов при реалистичной частоте, 60 клиентов синхронизации, события интеграции после доработки (параллельная обработка по случаям), отправка без клиентов для сравнения.
- **Клиенты:** долгий опрос `/sync` с фильтром веб-клиента (ленивая загрузка участников, 30 событий ленты) — так работает текущий веб-клиент.
- **Открытая модель нагрузки:** запросы уходят по расписанию, не дожидаясь ответов, — задержка сервера не снижает подаваемую нагрузку.
- **Задержка доставки** — от начала отправки до получения сообщения в синхронизации каждым другим участником комнаты.
- Генератор нагрузки работает на той же машине и тоже тратит процессор — цифры пессимистичны.

## 3. Результаты

### 3.1. Чаты случаев (A)

| Сценарий | p50 | p95 | p99 | Примечание |
|---|---|---|---|---|
| Снимки случаев `case.upserted`, пакет из 100 | 1,0 с | 1,3 с | — | 94 события/с (комнаты не создаются) |
| Создание чата, 2,5/с, 1600 чатов (11 мин) | 1,9 с | 3,0 с | 4,3 с | Близко к потолку — растёт очередь |
| Создание чата, 5/с (цель), 300 чатов | 22,7 с | 28,0 с | 28,2 с | Достигнуто 3,6 чата/с — очередь растёт всё время |
| Создание чата, 0,5/с, 100 чатов (прогон 2) | 0,63 с | **0,85 с** | 1,0 с | В цели |
| Создание чата, 1/с, 20 чатов (прогон 2) | 0,57 с | 1,1 с | — | На грани цели |
| Вход участника в чат (приглашение) | 0,9 с | 1,4 с | 1,6 с | 6700 входов, по 16 одновременно |

Один чат случая — около 12 событий состояния (создание, права, псевдоним, название, контекст, роли, 3–4 приглашения). Отдельный замер прямо в Synapse: `createRoom` по одному — 0,5 с, параллельно — **3,4–3,6 комнаты/с**, и от разных пользователей столько же. Значит, предел — запись событий в одном процессе Synapse, а не очередь на пользователя и не сервис контекста.

**Для планирования:** в регионе 1,5–2 тыс. новых чатов в сутки ([03-architecture.md, 9.3](03-architecture.md#93-оценка-нагрузки-для-планирования)) — в среднем 0,02 в секунду, в пиковый час — до 0,2. Даже этот стенд держит в 15 раз больше. Цель «5/с в течение часа» — с большим запасом; её закрывают воркеры записи событий (шардирование по комнатам) на продуктивном сервере.

### 3.2. События интеграции в существующие чаты (B)

| Сценарий | До доработки (прогон 1) | После (прогон 2) |
|---|---|---|
| Уведомления `notification.posted`, пакет из 50 | 14 событий/с, пакет p95 4,2 с | **34 события/с**, пакет p95 1,9 с |
| Обновления случаев `case.upserted`, пакет из 50 | 6 событий/с, пакет p95 9,5 с | **15 событий/с**, пакет p95 3,4 с |

Первый прогон показал, что сервис обрабатывал пакет **строго по одному событию**. Теперь события разных случаев обрабатываются параллельно (до 8 случаев), события одного случая — по порядку. Обновление случая с чатом — это 2–3 события состояния в комнате (контекст, роли, название), поэтому оно дороже уведомления.

### 3.3. Доставка сообщений (C)

Клиенты синхронизации работают одновременно, сообщения уходят в случайные чаты.

| Клиентов | Частота | Отправка p50 / p95 | Доставка p50 / p95 / p99 | Доставлено |
|---|---|---|---|---|
| 0 | 2 сообщения/с | 64 мс / 74 мс | — | — |
| 60 | 2 сообщения/с | 65 мс / 81 мс | 90 мс / **108 мс** / 275 мс | 100 % |
| 60 | 5 сообщений/с | 68 мс / 327 мс | 95 мс / 479 мс / 925 мс | 100 % |
| 240 | 2 сообщения/с | 75 мс / 588 мс | 107 мс / 721 мс / 1,3 с | 100 % |
| 240 | 10 сообщений/с | 88 мс / 882 мс | 125 мс / 1,3 с / 1,6 с | 100 % |
| 240 | 30 сообщений/с | 52 с / 57 с | 58 с / 69 с / 73 с | 100 % (перегрузка) |

- Сообщения не терялись ни на одной частоте.
- 30 сообщений/с — за пределом одного процесса Synapse на этой машине (116 % процессора у контейнера): очередь растёт, задержка — десятки секунд. Для сравнения: в регионе ожидается около 1 сообщения/с в среднем.
- Медиана в цели (≤ 300 мс) везде, хвост p95 растёт с числом клиентов. Диск ни при чём: без клиентов отправка — 74 мс (p95), `fsync` ≈ 0,3 мс. Хвост даёт конкуренция за процессор: один процесс Python и записывает события, и считает ответы сотням синхронизаций.

Simplified Sliding Sync (MSC4186) в Synapse 1.162 работает без дополнительной настройки: сервер отдаёт только видимое окно списка, поэтому время почти не зависит от числа комнат.

## 4. Что не проверено

- **Масштаб данных:** 1 млн комнат и 50 тыс. пользователей. При 3,5 комнаты/с наполнение заняло бы трое суток — нужен стенд с воркерами или загрузка синтетической базы.
- **2000 одновременных клиентов** и **часовой пик** — проверено 240 клиентов и 2–11 минут.
- **Synapse с воркерами**, отдельная машина для PostgreSQL, генератор нагрузки на отдельной машине.
- **Возврат в архивную комнату** — нет архивирования.
- **Tuwunel** вместо Synapse.

## 5. Что дальше

1. **Клиент — на Simplified Sliding Sync и локальное хранилище** (шаг 7 плана): холодный старт при сотнях комнат — доли секунды; после перезагрузки страницы — продолжение синхронизации, а не старт с нуля. Это снимает массовое переподключение.
2. **Продуктивная конфигурация Synapse:** воркеры синхронизации (2–4), 2 воркера записи событий (шардирование по комнатам), воркеры медиа и push, Redis, PostgreSQL на отдельной машине. Повторить этот прогон на целевом железе — по нему сайзинг.
3. **Наполнение до 1 млн комнат** на стенде с воркерами; проверка 2000 клиентов на Sliding Sync и часового пика 5 чатов/с.
4. **Исходящая очередь в сервисе контекста** (уже в плане): события и обратные вызовы не ждут друг друга.
5. Тот же прогон для **Tuwunel** — для решения по серверу.
